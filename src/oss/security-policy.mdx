LangChain 与各种外部资源（如本地和远程文件系统、API 和数据库）拥有庞大的集成生态系统。这些集成使开发者能够创建多功能的应用程序，将大型语言模型（LLM）的强大能力与访问、交互和操作外部资源的能力相结合。

## 最佳实践

在构建此类应用程序时，开发者应记住遵循良好的安全实践：

- [**限制权限**](https://en.wikipedia.org/wiki/Principle_of_least_privilege)：将权限严格限定在应用程序所需的范围内。授予广泛或过多的权限可能引入严重的安全漏洞。为避免此类漏洞，请根据应用程序的需要考虑使用只读凭证、不允许访问敏感资源、使用沙箱技术（如在容器中运行）、指定代理配置以控制外部请求等。

- **预判潜在滥用**：就像人类会犯错一样，大型语言模型（LLM）也可能犯错。始终假设任何系统访问或凭证可能以其被分配的权限所允许的任何方式被使用。例如，如果一对数据库凭证允许删除数据，最安全的做法是假设任何能够使用这些凭证的 LLM 实际上可能删除数据。

- [**纵深防御**](<https://en.wikipedia.org/wiki/Defense_in_depth_(computing)>)：没有任何安全技术是完美的。微调和良好的链设计可以减少，但不能消除，大型语言模型（LLM）犯错的可能性。最好结合多种分层安全方法，而不是依赖任何单一防御层来确保安全。例如：同时使用只读权限和沙箱来确保 LLM 只能访问明确允许它们使用的数据。

不这样做可能带来的风险包括但不限于：

- 数据损坏或丢失。
- 机密信息被未授权访问。
- 关键资源的性能或可用性受损。

带有缓解策略的示例场景：

- 用户可能要求具有文件系统访问权限的代理删除不应删除的文件或读取包含敏感信息的文件内容。作为缓解措施，请将代理限制为仅使用特定目录，并仅允许其读取或写入可以安全读取或写入的文件。进一步考虑通过在容器中运行代理来对其进行沙箱化。
- 用户可能要求具有外部 API 写访问权限的代理向 API 写入恶意数据或从该 API 删除数据。作为缓解措施，请为代理提供只读 API 密钥，或将其限制为仅使用已经对此类滥用具有抵抗力的端点。
- 用户可能要求具有数据库访问权限的代理删除表或更改架构。作为缓解措施，请将凭证限定为仅访问代理需要访问的表，并考虑颁发只读凭证。

如果你正在构建访问文件系统、API 或数据库等外部资源的应用程序，请考虑与公司的安全团队沟通，以确定如何最好地设计和保护你的应用程序。

## 报告 OSS 漏洞

请使用以下流程报告与 LangChain 开源项目相关的安全漏洞：

1. 在存在漏洞的 GitHub 仓库的 Security（安全）标签页上**提交安全咨询**。
2. **发送电子邮件**至 `security@langchain.dev`，通知我们你已提交安全 issue，以及该 issue 提交到了哪个仓库。

在报告漏洞之前，请查看上面的[最佳实践](#最佳实践)，以了解我们认为什么是安全漏洞与开发者责任。

### Bug 赏金资格

我们欢迎所有 LangChain 库的安全漏洞报告。但是，我们可能只为以下包中的漏洞提供临时 bug 赏金：

- 由 LangChain 团队拥有和维护的核心库：`langchain-core`、`langchain`（v1）、`langgraph` 以及相关的检查点包（或其 JavaScript 等价物）
- 由 LangChain 团队维护的流行集成（例如 `langchain-openai`、`langchain-anthropic` 等，或其 JavaScript 等价物）

漏洞必须在库代码本身中，而非示例代码或示例应用程序中。

我们欢迎所有其他 LangChain 包的报告，并将处理有效的安全问题，但超出此范围的包将不会获得 bug 赏金。这包括 `langchain-community`，由于其社区驱动的性质，不符合 bug 赏金资格，但我们将接受和处理其报告。

### 超出范围的目标

以下内容不纳入安全漏洞报告的范围：

- **langchain-experimental**：此仓库用于实验代码，不在安全报告范围内（请参阅[包警告](https://pypi.org/project/langchain-experimental/)）。
- **示例和示例应用程序**：示例代码和演示应用程序不在安全报告范围内。
- **标有安全通知的代码**：这将根据具体情况进行决定，但由于代码已附有开发人员应遵循的指南以确保其应用程序安全，可能不在范围内。
- **LangSmith 相关仓库或 API**：请参阅下面的[报告 LangSmith 漏洞](#报告-langsmith-漏洞)。
