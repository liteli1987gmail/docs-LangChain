多代理系统协调专门的组件来处理复杂的工作流程。然而，并非每个复杂任务都需要这种方法——具有正确（有时是动态）工具和提示词的单个代理通常可以达到类似的结果。

## 为什么使用多代理？

当开发者说他们需要"多代理"时，他们通常是在寻找以下一种或多种能力：

- <Icon icon="brain" /> **上下文管理**：提供专门知识而不会使模型的上下文窗口过载。如果上下文是无限的且延迟为零，你可以将所有知识放入一个提示词中——但由于并非如此，你需要选择性地呈现相关信息的模式。
- <Icon icon="users" /> **分布式开发**：允许不同团队独立开发和维护能力，将它们组合成具有清晰边界的大型系统。
- <Icon icon="git-branch" /> **并行化**：为子任务生成专门的工作者并并发执行以获得更快的成果。

当单个代理有太多[工具](/oss/langchain/tools)并对其使用做出糟糕决策时、当任务需要具有广泛上下文（长提示词和领域特定工具）的专门知识时，或者当你需要强制执行顺序约束以在满足某些条件后解锁能力时，多代理模式特别有价值。

<Tip>
多代理设计的核心是**[上下文工程](/oss/langchain/context-engineering)**——决定每个代理看到什么信息。系统的质量取决于确保每个代理可以访问其任务所需的正确数据。
</Tip>

## 模式

以下是构建多代理系统的主要模式，每种模式适合不同的用例：

| 模式 | 工作方式 |
|--------------|--------------|
| [**子代理**](/oss/langchain/multi-agent/subagents) | 主代理将子代理作为工具协调。所有路由都通过主代理，主代理决定何时以及如何调用每个子代理。 |
| [**交接**](/oss/langchain/multi-agent/handoffs) | 行为根据状态动态变化。工具调用更新触发路由或配置更改的状态变量，切换代理或调整当前代理的工具和提示词。 |
| [**技能**](/oss/langchain/multi-agent/skills) | 按需加载专门的提示词和知识。单个代理保持控制权，同时根据需要从技能中加载上下文。 |
| [**路由器**](/oss/langchain/multi-agent/router) | 路由步骤对输入进行分类并将其定向到一个或多个专门代理。结果被合成为组合响应。 |
| [**自定义工作流**](/oss/langchain/multi-agent/custom-workflow) | 使用 [LangGraph](/oss/langgraph/overview) 构建定制执行流程，混合确定性逻辑和代理行为。将其他模式作为工作流中的节点嵌入。 |

- **分布式开发**：不同团队能否独立维护组件？
- **并行化**：多个代理能否并发执行？
- **多跳**：该模式是否支持连续调用多个子代理？
- **直接用户交互**：子代理能否直接与用户对话？

<Tip>
    你可以混合模式！例如，**子代理**架构可以调用执行自定义工作流或路由器代理的工具。子代理甚至可以使用**技能**模式按需加载上下文。可能性是无穷无尽的！
</Tip>

## 性能比较

不同的模式具有不同的性能特征。了解这些权衡有助于你为延迟和成本需求选择正确的模式。

**关键指标：**
- **模型调用**：大型语言模型调用次数。更多调用 = 更高的延迟（特别是如果是顺序的）和更高的每次请求 API 成本。
- **处理的 token**：所有调用中总的[上下文窗口](/oss/langchain/context-engineering)使用量。更多 token = 更高的处理成本和潜在的上下文限制。

### 重复请求

> **第 1 轮：** "买咖啡"
> **第 2 轮：** "再买咖啡"

用户在同一对话中重复相同的请求。

<div className="compact-first-col">

| 模式 | 第 2 轮调用 | 总计（两轮） | 最佳适配 |
|---------|:------------:|:------------------:|:--------:|
| [**子代理**](/oss/langchain/multi-agent/subagents) | 4 | 8 | |
| [**交接**](/oss/langchain/multi-agent/handoffs) | 2 | 5 | ✅ |
| [**技能**](/oss/langchain/multi-agent/skills) | 2 | 5 | ✅ |
| [**路由器**](/oss/langchain/multi-agent/router) | 3 | 6 | |

</div>

<Tabs>
  <Tab title="子代理">
    **再次 4 次调用 → 8 次总计**
    - 子代理**按设计是无状态的**——每次调用遵循相同的流程
    - 主代理维护对话上下文，但子代理每次都是全新的开始
    - 这提供了强大的上下文隔离但重复完整流程
  </Tab>

  <Tab title="交接">
    **2 次调用 → 5 次总计**
    - 咖啡代理**从第 1 轮开始仍然活跃**（状态持久化）
    - 无需交接——代理直接调用 `buy_coffee` 工具（调用 1）
    - 代理响应用户（调用 2）
    - **通过跳过交接节省 1 次调用**
  </Tab>

  <Tab title="技能">
    **2 次调用 → 5 次总计**
    - 技能上下文**已加载到对话历史中**
    - 无需重新加载——代理直接调用 `buy_coffee` 工具（调用 1）
    - 代理响应用户（调用 2）
    - **通过重用加载的技能节省 1 次调用**
  </Tab>

  <Tab title="路由器">
    **再次 3 次调用 → 6 次总计**
    - 路由器是**无状态的**——每个请求都需要大型语言模型路由调用
    - 第 2 轮：路由器大型语言模型调用 (1) → Milk 代理调用 buy_coffee (2) → Milk 代理响应 (3)
    - 可以通过包装为有状态代理的工具来优化
  </Tab>
</Tabs>

**关键洞察：** 有状态模式（交接、技能）在重复请求上节省 40-50% 的调用。子代理保持一致的每次请求成本——这种无状态设计在重复模型调用的成本上提供了强大的上下文隔离。

### 多领域

> **用户：** "比较用于 Web 开发的 Python、JavaScript 和 Rust"

每个语言代理/技能包含约 2000 个 token 的文档。所有模式都可以进行并行工具调用。

| 模式 | 模型调用 | 总 token | 最佳适配 |
|---------|:-----------:|:------------:|:--------:|
| [**子代理**](/oss/langchain/multi-agent/subagents) | 5 | ~9K | ✅ |
| [**交接**](/oss/langchain/multi-agent/handoffs) | 7+ | ~14K+ | |
| [**技能**](/oss/langchain/multi-agent/skills) | 3 | ~15K | |
| [**路由器**](/oss/langchain/multi-agent/router) | 5 | ~9K | ✅ |

<Tabs>
  <Tab title="子代理">
    **5 次调用，~9K token**

    <Frame>
      <img src="/oss/langchain/multi-agent/images/multidomain-subagents.png" alt="Subagents multi-domain: 5 calls with parallel execution" />
    </Frame>

    每个子代理在**隔离**中工作，只有其相关上下文。总计：**9K token**。
  </Tab>

  <Tab title="交接">
    **7+ 次调用，~14K+ token**

    <Frame>
      <img src="/oss/langchain/multi-agent/images/multidomain-handoffs.png" alt="Handoffs multi-domain: 7+ sequential calls" />
    </Frame>

    交接**顺序**执行——无法并行研究所有三种语言。不断增长的对话历史会增加开销。总计：**~14K+ token**。
  </Tab>

  <Tab title="技能">
    **3 次调用，~15K token**

    <Frame>
      <img src="/oss/langchain/multi-agent/images/multidomain-skills.png" alt="Skills multi-domain: 3 calls with accumulated context" />
    </Frame>

    加载后，**每次后续调用处理所有 6K token 的技能文档**。子代理由于上下文隔离而处理少 67% 的 token。总计：**15K token**。
  </Tab>

  <Tab title="路由器">
    **5 次调用，~9K token**

    <Frame>
      <img src="/oss/langchain/multi-agent/images/multidomain-router.png" alt="Router multi-domain: 5 calls with parallel execution" />
    </Frame>

    路由器使用**大型语言模型进行路由**，然后并行调用代理。类似于子代理但具有明确的路由步骤。总计：**9K token**。
  </Tab>
</Tabs>

**关键洞察：** 对于多领域任务，并行执行的模式（子代理、路由器）效率最高。技能调用次数较少，但由于上下文积累导致 token 使用量高。交接效率低——必须顺序执行，无法利用并行工具调用同时咨询多个领域。
