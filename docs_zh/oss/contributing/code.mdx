### 快速修复：提交错误修复

对于简单的错误修复，你可以立即开始：

<Steps>
    <Step title="重现问题">
        在克隆仓库之前，确保你能可靠地重现这个 bug。这有助于确认问题，并为你的修复提供起点。维护者和其他贡献者应该能够根据你的描述重现问题，而不需要额外的设置或修改。
    </Step>

    <Step title="Fork 仓库">
        :::python
        Fork [LangChain](https://github.com/langchain-ai/langchain)、[LangGraph](https://github.com/langchain-ai/langgraph) 或 [Deep Agents](https://github.com/langchain-ai/deepagents) 仓库到你个人的 GitHub 账户<Tooltip tip="如果你 fork 到组织账户，维护者将无法进行编辑，这可能会大大延迟接受。">personal GitHub account</Tooltip>
        :::
        :::js
        Fork [LangChain](https://github.com/langchain-ai/langchainjs)、[LangGraph](https://github.com/langchain-ai/langgraphjs) 或 [Deep Agents](https://github.com/langchain-ai/deepagentsjs) 仓库到你个人的 GitHub 账户<Tooltip tip="如果你 fork 到组织账户，维护者将无法进行编辑，这可能会大大延迟接受">personal GitHub account</Tooltip>
        :::
    </Step>

    <Step title="克隆并设置">
        :::python

        ```bash
        git clone https://github.com/your-username/name-of-forked-repo.git

        # 例如，对于 LangChain：
        git clone https://github.com/parrot123/langchain.git
        ```

        ```bash
        # 在你的仓库中，初始化环境并安装依赖
        uv venv && source .venv/bin/activate
        uv sync --all-groups

        # 或者，只安装特定的组：
        uv sync --group test
        ```

        如果你之前没有安装过，你需要安装 [`uv`](https://docs.astral.sh/uv/)
        :::
        :::js

        ```bash
        git clone https://github.com/your-username/name-of-forked-repo.git

        # 例如，对于 LangChain：
        git clone https://github.com/parrot123/langchainjs.git

        # 对于 LangGraph：
        git clone https://github.com/parrot123/langgraphjs.git
        ```

        ```bash
        # 在你的仓库中，安装依赖
        pnpm install
        # 为所有包创建构建以解析工作区依赖
        pnpm build
        ```
        :::
    </Step>

    <Step title="创建分支">
        为你的修复创建一个新分支。这有助于保持你的更改有条理，也方便以后提交拉取请求。

        ```bash
        git checkout -b your-username/short-bugfix-name
        ```
    </Step>

    <Step title="编写失败的测试">
        添加[单元测试](#test-writing-guidelines)，这些测试在没有你的修复的情况下会失败。这允许我们验证 bug 已解决并防止回归
    </Step>

    <Step title="进行更改">
        在遵循我们的[代码质量标准](#code-quality-standards)的同时修复 bug。进行**解决该问题所需的最小更改**。我们强烈鼓励贡献者在开始编码之前在 issue 上发表评论。例如：

        > *"我想处理这个。我打算的方法是[...简要描述...]。这是否符合维护者的期望？"*

        30 秒的评论通常可以防止你的初步方法错误时浪费精力。
    </Step>

    :::js
    <Step title="运行构建">
        运行构建命令以确保包仍然正确构建
        ```bash
        pnpm build
        # 或构建特定的工作区包
        pnpm --filter @langchain/core build
        ```
    </Step>
    :::

    <Step title="验证修复">
        确保测试通过且没有引入回归。在提交 PR 之前确保所有测试在本地都通过

        :::python

        ```bash
        make format
        make lint
        make test

        # 对于涉及集成的错误修复，还要运行：
        make integration_tests
        # （你可能需要设置 API 测试凭据）
        ```
        :::
        :::js

        ```bash
        pnpm lint
        pnpm test

        # 对于涉及集成的错误修复，还要运行：
        pnpm test:int

        # 或者在特定的工作区包中运行测试
        cd libs/langchain-core
        pnpm test
        pnpm lint

        # 或者从仓库根目录运行特定包的测试
        pnpm --filter @langchain/core test
        pnpm --filter @langchain/core lint
        ```
        :::
    </Step>

    <Step title="记录更改">
        如果行为有变化，更新文档字符串和/或内联注释
    </Step>

    <Step title="提交拉取请求">
        遵循提供的 PR 模板。如果适用，使用[关闭关键字](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#linking-a-pull-request-to-an-issue-using-a-keyword)引用你要修复的问题（例如 `Fixes #ISSUE_NUMBER`），这样当你的 PR 被合并时问题会自动关闭。
    </Step>
</Steps>

## 贡献指南

在开始为 LangChain 项目做贡献之前，花点时间想想你为什么要这样做。如果你的唯一目标是在你的简历上添加一个"首次贡献"（或者你只是在寻找一个快速胜利），你可能最好参加一个训练营或在线教程。

为开源项目做贡献需要时间和精力，但它也可以帮助你成为更好的开发者并学习新技能。然而，重要的是要知道，这可能比参加培训课程更难更慢。也就是说，如果你愿意花时间把事情做好，开源贡献是值得的！

### 向后兼容性

<Warning>
除关键安全修复外，不允许对公共 API 进行破坏性更改。

有关主要版本发布的详细信息，请参阅我们的[版本控制策略](/oss/versioning)。
</Warning>

通过以下方式保持兼容性：

<AccordionGroup>
    <Accordion title="稳定接口">
        **始终保留**：

        - 函数签名和参数名称
        - 类接口和方法名称
        - 返回值结构和类型
        - 公共 API 的导入路径
    </Accordion>

    <Accordion title="安全更改">
        **可接受的修改**：

        :::python
        - 添加新的可选参数
        :::
        :::js
        - 添加新的可选参数/类型参数
        :::
        - 向类添加新方法
        - 在不改变行为的情况下改进性能
        - 添加新模块或函数
    </Accordion>

    <Accordion title="在进行更改之前">
        - **这会破坏现有用户代码吗？**
        - 检查你的目标是否是公共的
        :::python
        - 如果需要，它在 `__init__.py` 中导出了吗？
        :::
        - 测试中是否有现有的使用模式？
    </Accordion>
</AccordionGroup>

### 新功能

我们对新功能保持高标准。一般来说，我们不接受没有现有 issue 证明其迫切需要的外部贡献者的新核心抽象。这同样适用于基础设施和依赖项的更改。

一般来说，功能贡献要求包括：

<Steps>
    <Step title="设计讨论">
        开一个 issue 描述：

        - 你正在解决的问题
        - 提议的 API 设计
        - 预期的使用模式
    </Step>

    <Step title="实现">
        - 遵循现有代码模式
        - 包含全面的测试和文档
        - 考虑安全影响
    </Step>

    <Step title="集成注意事项">
        - 这如何与现有功能交互？
        - 是否有性能影响？
        - 这是否引入了新的依赖项？

        我们将拒绝可能导致安全漏洞或报告的功能。
    </Step>
</Steps>

### 安全指南

<Warning>
安全至关重要。绝不引入漏洞或不安全的模式。
</Warning>

安全检查清单：

<AccordionGroup>
    <Accordion title="输入验证">
        - 验证和清理所有用户输入
        - 在模板和查询中正确转义数据
        :::python
        - 永远不要对用户数据使用 `eval()`、`exec()` 或 `pickle`，因为这可能导致任意代码执行漏洞
        :::
        :::js
        - 永远不要使用 `eval()`，因为这可能导致任意代码执行漏洞
        :::
    </Accordion>

    <Accordion title="错误处理">
        - 使用特定的异常类型
        - 不要在错误消息中暴露敏感信息
        - 实现适当的资源清理
    </Accordion>

    <Accordion title="依赖项">
        - 避免添加硬依赖
        - 保持可选依赖最小化
        - 审查第三方包的安全问题
    </Accordion>
</AccordionGroup>

## 开发工作流程

### 预提交钩子

:::python
[LangChain](https://github.com/langchain-ai/langchain) 和 [Deep Agents](https://github.com/langchain-ai/deepagents) 仓库包含[预提交](https://pre-commit.com/)钩子，在每次提交前自动运行格式化、linting 和验证检查。从仓库根目录安装它们：

```bash
pip install pre-commit  # 或：uv tool install pre-commit
pre-commit install
```

钩子强制执行：
- 不直接提交到受保护分支
- YAML 和 TOML 语法验证
- 尾随空白和文件结尾修复
- 智能引号和非标准空格规范化
- 每个包的 `make format` 和 `make lint`
:::

### 运行测试

<Info>
目录是相对于你正在工作的包。
</Info>

我们尽可能倾向于单元测试而不是集成测试。单元测试在每次拉取请求时运行，所以它们应该快速可靠。集成测试按计划运行，需要更多设置，所以应该保留用于确认与外部服务的接口点。

#### 单元测试

:::python
**位置**：`tests/unit_tests/`
:::
:::js
**位置**：`src/tests/FILENAME_BEING_TESTED.test.ts`
:::

单元测试覆盖不需要调用外部 API 的模块化逻辑。如果你添加了新逻辑，应该添加单元测试。在单元测试中，检查预处理/后处理并模拟外部依赖。

**要求**：
- 不允许网络调用
- 测试所有代码路径，包括边缘情况
- 使用 mock 处理外部依赖

运行单元测试：

:::python
```bash
make test

# 或直接：
uv run --group test pytest tests/unit_tests

# 运行特定测试：
TEST_FILE=tests/unit_tests/test_imports.py make test
```
:::
:::js
```bash
# 运行整个测试套件
pnpm test

# 或运行特定测试文件
pnpm test src/tests/FILENAME_BEING_TESTED.test.ts

# 或运行特定测试函数
pnpm test -t "the test that should be run"
```
:::

#### 集成测试

:::python
**位置**：`tests/integration_tests/`
:::
:::js
**位置**：`src/tests/FILENAME_BEING_TESTED.int.test.ts`
:::

集成测试覆盖需要调用外部 API 的逻辑（通常是与其他服务的集成）。

集成测试需要访问外部服务/提供商 API（可能需要花钱），因此默认不运行。

并不是每个代码更改都需要集成测试，但请记住，我们会单独要求/运行集成测试作为我们审查流程的一部分。

**要求**：
- 使用外部服务测试真实集成
- 使用环境变量处理 API 密钥
- 如果凭据不可用则优雅地跳过

运行集成测试：
:::python
```bash
make integration_tests

# 或直接：
```

### 依赖项

LangChain 包区分**硬依赖**和**可选依赖**，以保持包轻量级并最小化用户的安装开销。

<Tabs>
    <Tab title="可选依赖">
        几乎所有新依赖都应该是可选的。在以下情况下使用可选依赖：

        - 依赖项仅用于特定集成或功能
        - 用户可以在没有此依赖的情况下有意义地使用包
        - 依赖项很大或有很深的传递依赖

        **要求：**

        - 未安装依赖的用户必须能够**导入**你的代码而没有任何副作用（无警告、无错误、无异常）
        - `pyproject.toml` 和 `uv.lock` **不会**被修改

        **添加可选依赖：**

        1. 将依赖添加到适当的测试依赖文件（例如 `extended_testing_deps.txt`）
        2. 添加一个至少尝试导入新代码的单元测试。理想情况下，单元测试使用轻量级 fixtures 来测试代码的逻辑。
        3. 对任何需要依赖的单元测试使用 `@pytest.mark.requires("package_name")` 装饰器。
    </Tab>

    <Tab title="硬依赖">
        硬依赖在用户安装包时自动安装。仅在以下情况下使用硬依赖：

        - 包在没有依赖的情况下根本无法运行
        - 依赖很小且几乎没有传递依赖
        - 没有合理的方法使功能成为可选的

        <Warning>
            添加硬依赖会增加所有用户的安装时间和潜在版本冲突。

            维护者将仔细审查硬依赖添加！
        </Warning>

        **添加硬依赖：**

        1. 开一个 issue 或讨论，解释为什么依赖必须是硬依赖而不是可选的
        2. 在 `pyproject.toml` 的适当部分下添加依赖
        3. 运行 `uv lock` 更新锁文件
        4. 包含涵盖新功能的全面测试
    </Tab>
</Tabs>

### 测试编写指南

为了编写有效的测试，需要遵循一些最佳实践：

:::python
- 使用自然语言在文档字符串中描述测试
- 使用描述性的变量名称
- 详尽地进行断言
:::
:::js
- 将测试封装在描述被测试组件的 `describe` 块中
- 使用自然语言描述测试名称
- 详尽地进行断言
- 仅对大小合理的数据对象使用快照
:::

<Tabs>
    <Tab title="单元测试">
        :::python
        ```python
        def test_document_processor_handles_empty_input():
            """Test processor gracefully handles empty document list."""
            processor = DocumentProcessor()

            result = processor.process([])

            assert result.success
            assert result.processed_count == 0
            assert len(result.errors) == 0
        ```
        :::
        :::js
        ```typescript
        describe("DocumentProcessor", () => {
            it("Should handle empty document list", () => {
                const processor = new DocumentProcessor();
                const result = processor.process([]);

                expect(result.success).toBe(true);
                expect(result.processedCount).toBe(0);
                expect(result.errors).toHaveLength(0);
            });
        });
        ```
        :::
    </Tab>

    <Tab title="集成测试">
        :::python
        ```python
        @pytest.mark.requires("openai")
        def test_openai_chat_integration():
            """Test OpenAI chat integration with real API."""

            chat = ChatOpenAI()
            response = chat.invoke("Hello")

            assert isinstance(response.content, str)
            assert len(response.content) > 0
        ```
        :::
        :::js
        ```typescript
        describe("ChatOpenAI", () => {
            it("Should test with real API", () => {
                const chat = new ChatOpenAI();
                const response = chat.invoke("Hello");
            });
        });
        ```

        ```python
        def test_retry_mechanism(mocker):
        ```
