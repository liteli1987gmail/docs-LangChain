自托管 LangSmith 实例可以处理大量追踪和用户。自托管部署的默认配置可以处理大量负载，你可以配置你的部署以实现更高的规模。本页描述了扩展注意事项并提供了一些示例来帮助配置你的自托管实例。

有关示例配置，请参阅 [LangSmith 规模化示例配置](#example-langsmith-configurations-for-scale)。

## 追踪摄入（写入路径）

给写入路径带来负载的常见用法：

- 通过 Python 或 JavaScript LangSmith SDK 摄入追踪
- 通过 `@traceable` 包装器摄入追踪
- 通过 `/runs/multipart` 端点提交追踪

在追踪摄入中起重要作用的 服务：

- 平台后端服务：接收摄入追踪的初始请求并将追踪放入 Redis 队列
- Redis 缓存：用于排队需要持久化的追踪
- 摄入队列服务：将追踪持久化以供查询
- ClickHouse：用于追踪的持久化存储

当扩展写入路径（追踪摄入）时，监控上述四个服务/资源会很有帮助。以下是一些可以帮助提高追踪摄入性能的典型更改：

- 如果 ClickHouse 接近资源限制，请为其提供更多资源（CPU 和内存）。
- 如果摄入请求响应时间较长，请增加 platform-backend pod 的数量。
- 如果追踪从 Redis 处理的速度不够快，请增加摄入队列服务 pod 副本。
- 如果你注意到当前 Redis 实例达到资源限制，请使用更大的 Redis 缓存。这也可能是摄入请求耗时长的原因。

## 追踪查询（读取路径）

给读取路径带来负载的常见用法：

- 用户在前端查看追踪项目或单个追踪
- 用于查询追踪信息的脚本
- 访问 `/runs/query` 或 `/runs/<run-id>` api 端点

在查询追踪中起重要作用的 服务：

- 后端服务：接收请求并向 ClickHouse 提交查询以响应请求
- ClickHouse：追踪的持久化存储。这是请求追踪信息时查询的主要数据库。

当扩展读取路径（追踪查询）时，监控上述两个服务/资源会很有帮助。以下是一些可以帮助提高追踪查询性能的典型更改：

- 增加后端服务 pod 的数量。如果后端服务 pod 达到 1 核心 CPU 使用率，这将最有影响力。
- 为 ClickHouse 提供更多资源（CPU 或内存）。ClickHouse 可能非常占用资源，但这应该会带来更好的性能。
- 转移到[复制 ClickHouse 集群](/langsmith/self-host-external-clickhouse#ha-replicated-clickhouse-cluster)。添加 ClickHouse 副本有助于读取性能，但我们建议保持在 5 个副本以下（从 3 个开始）。

有关如何将其转化为 helm chart values 的更精确指导，请参阅以下[部分](#example-langsmith-configurations-for-scale)中的示例。如果你不确定为什么你的 LangSmith 实例无法处理某种负载模式，请联系 LangChain 团队。

## LangSmith 队列的 KEDA 自动扩展

<Note>
LangSmith v0.13.0 及更高版本可用。
</Note>

我们强烈建议在你的集群上安装 [KEDA](https://keda.sh/)（Kubernetes 事件驱动自动扩展）。KEDA 使 `queue` 和 `ingest-queue` 服务能够根据其队列积压大小以及 CPU 和内存自动扩展。这可以带来更有效的资源利用和更好的流量峰值处理。

### 安装 KEDA

```bash
helm repo add kedacore https://kedacore.github.io/charts
helm install keda kedacore/keda --namespace keda --create-namespace
```

### 配置 KEDA 自动扩展

安装 KEDA 后，你可以在 `values.yaml` 中为 `queue` 和 `ingest-queue` 服务启用基于 KEDA 的自动扩展：

```yaml
queue:
  autoscaling:
    keda:
      enabled: true

ingestQueue:
  autoscaling:
    keda:
      enabled: true
```

启用 KEDA 后，队列服务会在其积压增长时自动扩展，并在处理积压时缩减。这对于处理可变的追踪摄入负载而无需过度配置资源特别有用。

<Note>
你也可以为其他服务（`backend`、`platformBackend` 等）启用 KEDA，但它们仍仅通过 CPU 和内存进行扩展。
</Note>

## LangSmith 规模化示例配置

下面我们根据预期的读取和写入负载提供一些 LangSmith 配置示例。

对于读取负载（追踪查询）：

- 低意味着大约 5 个用户同时查看追踪（约每秒 10 个请求）
- 中意味着大约 20 个用户同时查看追踪（约每秒 40 个请求）
- 高意味着大约 50 个用户同时查看追踪（约每秒 100 个请求）

对于写入负载（追踪摄入）：

- 低意味着每秒最多 10 条追踪
- 中意味着每秒最多 100 条追踪
- 高意味着每秒最多 1000 条追踪

<Note>
确切的最佳配置取决于你的使用情况和追踪有效载荷。将下面的示例与上述信息和你特定的用法相结合，以你认为合适的方式更新你的 LangSmith 配置。如果你有任何问题，请联系 LangChain 团队。
</Note>

### 低读取，低写入 <a name="low-reads-low-writes"></a>

默认的 LangSmith 配置将处理此负载。不需要自定义资源配置。

### 低读取，高写入 <a name="low-reads-high-writes"></a>

你有非常大规模的追踪摄入，但任何时候前端查询追踪的用户都是个位数。

对于此，我们建议使用如下配置：

```yaml
config:
  blobStorage:
    # 请同时设置其他密钥以连接到你的 blob 存储。请参阅配置部分。
    enabled: true
  settings:
    redisRunsExpirySeconds: "3600"
# ttl:
#   enabled: true
#   ttl_period_seconds:
#     longlived: "7776000"  # 90 天（默认是 400 天）
#     shortlived: "604800"  # 7 天（默认是 14 天）

frontend:
  deployment:
    replicas: 4 # 或在下面启用 autoscaling
# autoscaling:
#   hpa:
#     enabled: true
#     minReplicas: 2
#     maxReplicas: 4

platformBackend:
  deployment:
    replicas: 20 # 或在下面启用 autoscaling
# autoscaling:
#   hpa:
#     enabled: true
#     minReplicas: 8
#     maxReplicas: 20

ingestQueue:
  deployment:
    replicas: 24 # 或在下面启用 KEDA autoscaling
# autoscaling:
#   keda:
#     enabled: true
#     minReplicaCount: 8
#     maxReplicaCount: 24

backend:
  deployment:
    replicas: 5 # 或在下面启用 autoscaling
# autoscaling:
#   hpa:
#     enabled: true
#     minReplicas: 3
#     maxReplicas: 5

## 确保你的 Redis 缓存至少为 26 GB 以应对高写入规模
redis:
  external:
    enabled: true
    existingSecretName: langsmith-redis-secret # 为你的外部 Redis 实例设置连接 url（26+ GB）

clickhouse:
  statefulSet:
    persistence:
      # 这可能取决于你配置的 TTL（请参阅配置部分）。
      # 如果持续以此规模运行，我们建议每个短期 TTL 天使用 600Gi。
      size: 4200Gi # 这假设 7 天 TTL 并持续以此规模运行。
    resources:
      requests:
        cpu: "10"
        memory: "32Gi"
      limits:
        cpu: "16"
        memory: "48Gi"

commonEnv:
  - name: "CLICKHOUSE_ASYNC_INSERT_WAIT_PCT_FLOAT"
    value: "0"
```

### 高读取，低写入 <a name="high-reads-low-writes"></a>

你的追踪摄入规模相对较低，但有许多前端用户查询追踪和/或脚本频繁访问 `/runs/query` 或 `/runs/<run-id>` 端点。

**对于此，我们强烈建议设置复制 ClickHouse 集群以在低延迟下实现高读取规模。** 有关如何设置复制 ClickHouse 集群的更多指导，请参阅我们的[外部 ClickHouse 文档](/langsmith/self-host-external-clickhouse#ha-replicated-clickhouse-cluster)。对于此负载模式，我们建议使用 3 节点复制设置，集群中的每个副本应具有 8+ 核心和 16+ GB 内存的资源请求，以及 12 核心和 32 GB 内存的资源限制。

对于此，我们建议使用如下配置：

```yaml
config:
  blobStorage:
    # 请同时设置其他密钥以连接到你的 blob 存储。请参阅配置部分。
    enabled: true

frontend:
  deployment:
    replicas: 2

ingestQueue:
  deployment:
    replicas: 3 # 或在下面启用 KEDA autoscaling
# autoscaling:
#   keda:
#     enabled: true
#     minReplicaCount: 2
#     maxReplicaCount: 3

backend:
  deployment:
    replicas: 40 # 或在下面启用 autoscaling
# autoscaling:
#   hpa:
#     enabled: true
#     minReplicas: 16
#     maxReplicas: 40

# 我们强烈建议为此负载设置复制 clickhouse 集群。
# 根据需要更新这些值以连接到你的复制 clickhouse 集群。
clickhouse:
  external:
    # 如果使用 3 节点复制设置，每个副本应具有 8+ 核心和 16+ GB 内存的资源请求，以及 12 核心和 32 GB 内存的资源限制。
    enabled: true
    host: langsmith-ch-clickhouse-replicated.default.svc.cluster.local
    port: "8123"
    nativePort: "9000"
    user: "default"
    password: "password"
    database: "default"
    cluster: "replicated"
```

### 中读取，中写入 <a name="medium-reads-medium-writes"></a>

这是一个很好的全方位配置，应该能够处理 LangSmith 的大多数使用模式。在内部测试中，此配置允许我们扩展到每秒摄入 100 条追踪和每秒 40 个读取请求。

对于此，我们建议使用如下配置：

```yaml
config:
  blobStorage:
    # 请同时设置其他密钥以连接到你的 blob 存储。请参阅配置部分。
    enabled: true
  settings:
    redisRunsExpirySeconds: "3600"

frontend:
  deployment:
    replicas: 2

ingestQueue:
  deployment:
    replicas: 6 # 或在下面启用 KEDA autoscaling
# autoscaling:
#   keda:
#     enabled: true
#     minReplicaCount: 3
#     maxReplicaCount: 6

backend:
  deployment:
    replicas: 16 # 或在下面启用 autoscaling
# autoscaling:
#   hpa:
#     enabled: true
#     minReplicas: 8
#     maxReplicas: 16

redis:
  statefulSet:
    resources:
      requests:
        memory: 13Gi
      limits:
        memory: 13Gi

  # -- 对于外部 redis，改为使用如下内容 --
  # external:
  #   enabled: true
  #   connectionUrl: "<URL>" 或 existingSecretName: "<SECRET-NAME>"

clickhouse:
  statefulSet:
    persistence:
      # 这可能取决于你配置的 TTL。
      # 如果持续以此规模运行，我们建议每个短期 TTL 天使用 60Gi。
      size: 420Gi # 这假设 7 天 TTL 并持续以此规模运行。
    resources:
      requests:
        cpu: "16"
        memory: "24Gi"
      limits:
        cpu: "28"
        memory: "40Gi"

commonEnv:
  - name: "CLICKHOUSE_ASYNC_INSERT_WAIT_PCT_FLOAT"
    value: "0"
```

<Warning>
如果你仍然注意到上述配置读取缓慢，我们建议迁移到[复制 Clickhouse 集群设置](/langsmith/self-host-external-clickhouse#ha-replicated-clickhouse-cluster)
</Warning>

### 高读取，高写入 <a name="high-reads-high-writes"></a>

你有非常高的追踪摄入率（接近每秒 1000 条追踪），并且还有许多用户在前端查询追踪（超过 50 个用户）和/或脚本持续向 `/runs/query` 或 `/runs/<run-id>` 端点发出请求。

**对于此，我们非常强烈建议设置复制 ClickHouse 集群，以防止在高写入规模下读取性能下降。** 有关如何设置复制 ClickHouse 集群的更多指导，请参阅我们的[外部 ClickHouse 文档](/langsmith/self-host-external-clickhouse#ha-replicated-clickhouse-cluster)。对于此负载模式，我们建议使用 3 节点复制设置，其中每个副本应具有 14+ 核心和 24+ GB 内存的资源请求，以及 20 核心和 48 GB 内存的资源限制。我们还建议每个 ClickHouse 节点/实例每个 TTL 天拥有 600 Gi 的卷存储（如下面的配置）。

总体而言，我们建议使用如下配置：

```yaml
config:
  blobStorage:
    # 请同时设置其他密钥以连接到你的 blob 存储。请参阅配置部分。
    enabled: true
  settings:
    redisRunsExpirySeconds: "3600"
# ttl:
#   enabled: true
#   ttl_period_seconds:
#     longlived: "7776000"  # 90 天（默认是 400 天）
#     shortlived: "604800"  # 7 天（默认是 14 天）

frontend:
  deployment:
    replicas: 4 # 或在下面启用 autoscaling
# autoscaling:
#   hpa:
#     enabled: true
#     minReplicas: 2
#     maxReplicas: 4

platformBackend:
  deployment:
    replicas: 20 # 或在下面启用 autoscaling
# autoscaling:
#   hpa:
#     enabled: true
#     minReplicas: 8
#     maxReplicas: 20

ingestQueue:
  deployment:
    replicas: 24 # 或在下面启用 KEDA autoscaling
# autoscaling:
#   keda:
#     enabled: true
#     minReplicaCount: 8
#     maxReplicaCount: 24

backend:
  deployment:
    replicas: 50 # 或在下面启用 autoscaling
# autoscaling:
#   hpa:
#     enabled: true
#     minReplicas: 20
#     maxReplicas: 50

## 确保你的 Redis 缓存至少为 26 GB 以应对高写入规模
redis:
  external:
    enabled: true
    existingSecretName: langsmith-redis-secret # 为你的外部 Redis 实例设置连接 url（26+ GB）

# 我们强烈建议为此负载设置复制 clickhouse 集群。
# 根据需要更新这些值以连接到你的复制 clickhouse 集群。
clickhouse:
  external:
    # 如果使用 3 节点复制设置，每个副本应具有 14+ 核心和 24+ GB 内存的资源请求，以及 20 核心和 48 GB 内存的资源限制。
    enabled: true
    host: langsmith-ch-clickhouse-replicated.default.svc.cluster.local
    port: "8123"
    nativePort: "9000"
    user: "default"
    password: "password"
    database: "default"
    cluster: "replicated"

commonEnv:
  - name: "CLICKHOUSE_ASYNC_INSERT_WAIT_PCT_FLOAT"
    value: "0"
```

<Note>
确保 Kubernetes 集群配置有足够的资源以扩展到建议的大小。部署后，Kubernetes 集群中的所有 pod 都应处于 `Running` 状态。停留在 `Pending` 的 pod 可能表明你已达到节点池限制或需要更大的节点。

此外，确保部署在集群上的任何入口控制器能够处理所需的负载，以防止瓶颈。
</Note>
