本概述涵盖了与在 LangSmith 中管理用户、组织、工作区和应用程序相关的主题。

## 资源层次结构

### 组织

组织是 LangSmith 中用户的逻辑分组，定义了在所有工作区之间共享的设置。这些设置管理整个组织范围的关注点，而不是工作区内的单个项目。常见的组织级配置包括用户管理、单点登录（SSO）、OAuth 提供者配置、自定义角色创建、计费和使用跟踪。通常，每个公司有一个组织。一个组织可以有多个工作区。有关更多详细信息，请参阅[设置指南](/langsmith/set-up-hierarchy#set-up-an-organization)。

首次登录时，系统会自动为您创建一个个人组织。如果您想与他人协作，可以创建一个单独的组织并邀请您的团队成员加入。您的个人组织和共享组织之间有一些重要区别：

| 功能 | 个人 | 共享 |
| ------------------- | ------------------- | -------------------------------------------------------------------------------------------- |
| 最大工作区数 | 1 | 取决于计划（请参阅[定价页面](https://www.langchain.com/pricing-langsmith)） |
| 协作 | 无法邀请用户 | 可以邀请用户 |
| 计费：付费计划 | 仅开发者计划 | 其他所有计划可用 |

### 工作区

<Info>
工作区以前称为租户。在过渡期间，某些代码和 API 可能仍会引用旧名称。
</Info>

工作区是组织内用户和资源的逻辑分组。工作区通常用于隔离团队或业务单元，在项目及其相关资源之间提供分离。工作区分离了资源的信任边界和访问控制。用户在工作区级别被授予权限，这决定了他们对工作区中资源的访问权限，包括追踪项目、数据集、标注队列和提示词。有关设置的详细信息，请参阅[设置指南](/langsmith/set-up-hierarchy#set-up-a-workspace)，有关权限的详细信息，请参阅[工作区（RBAC）](/langsmith/administration-overview#workspace-roles-rbac)。

我们建议为组织中的每个团队创建一个单独的工作区。为了进一步组织资源，您可以使用[应用程序](#applications)在工作区内对资源进行分组。有关基于团队隔离需求的不同工作区组织模型的指导，请参阅[工作负载隔离](/langsmith/workload-isolation)。

### 应用程序

应用程序是工作区内资源的逻辑分组。应用程序通常是代理，但您可以将其用于团队内的任何项目。应用程序通过仅显示当前上下文中关联的应用程序资源来保持 UI 有序。

应用程序构建在[资源标签](/langsmith/administration-overview#resource-tags)之上，可用于使用 [ABAC](/langsmith/organization-workspace-operations#access-policies) 控制资源访问。

从 [LangSmith UI](https://smith.langchain.com) 主导航侧边栏切换应用程序。使用侧边栏顶部的**应用程序**下拉菜单选择一个应用程序。

任何资源都可以在不标记到应用程序的情况下创建。当选择**所有应用程序**选项时，这些资源将可见。

### 资源

资源是用于构建、运行和观察应用程序和代理的具体实体，例如追踪项目、提示词、数据集和部署。资源作用域为特定应用程序。

### 资源标签

资源标签允许您在工作区内进一步隔离资源，以便与 [ABAC](/langsmith/organization-workspace-operations#access-policies) 一起使用。每个标签是一个键值对，您可以将其分配给资源。

LangSmith 资源标签与云服务中的标签非常相似，例如 [AWS](https://docs.aws.amazon.com/tag-editor/latest/userguide/tagging.html)。

在 [LangSmith UI](https://smith.langchain.com) 中导航到**设置**，在侧边栏中选择**资源标签**页面。

## 用户管理和 RBAC

### 用户

用户是有权访问 LangSmith 的人。用户可以是一个或多个组织以及这些组织内工作区的成员。

组织成员在**设置**页面下的**成员和角色**中管理。

工作区成员在**工作区**页面下的**设置**中管理。

### API 密钥

<Warning>
我们在 2024 年 10 月 22 日结束了对带有 `ls__` 前缀的传统 API 密钥的支持，转而使用个人访问令牌（PAT）和服务密钥。我们要求所有新集成使用 PAT 和服务密钥。带有 `ls__` 前缀的 API 密钥将从 2024 年 10 月 22 日起不再工作。
</Warning>

#### 过期日期

创建 API 密钥时，您可以选择设置过期日期。为密钥添加过期日期可以增强安全性并最大限度地降低未经授权访问的风险。例如，您可以为需要提升访问权限的临时任务设置密钥过期日期。

默认情况下，密钥永不过期。一旦过期，API 密钥将不再有效，无法重新激活或修改其过期时间。

#### 个人访问令牌（PAT）

个人访问令牌（PAT）用于对 LangSmith API 的请求进行身份验证。它们由用户创建并作用域用户。PAT 将具有与其创建者相同的权限。我们建议不要使用这些来对应用程序的请求进行身份验证，而是将它们用于与 LangSmith API 交互的个人脚本或工具。如果与 PAT 关联的用户从组织中移除，PAT 将不再工作。

PAT 以 `lsv2_pt_` 为前缀

#### 服务密钥

服务密钥类似于 PAT，但用于代表服务账户对 LangSmith API 的请求进行身份验证。只有管理员可以创建服务密钥。我们建议将这些用于需要与 LangSmith API 交互的应用程序/服务，例如 LangGraph 代理或其他集成。服务密钥可以作用域单个工作区、多个工作区或整个组织，并可用于对具有访问权限的工作区的 LangSmith API 进行身份验证。

服务密钥以 `lsv2_sk_` 为前缀

<Warning>
使用 `X-Tenant-Id` 头指定目标工作区。

- **使用 PAT 时**：如果省略此头，请求将在与密钥关联的默认工作区上运行。
- **使用组织作用域服务密钥时**：访问工作区作用域资源时必须包含 `X-Tenant-Id` 头。否则，请求将失败并显示 `403 Forbidden` 错误。
</Warning>

<Note>
要了解如何创建服务密钥或个人访问令牌，请参阅[设置指南](/langsmith/create-account-api-key)
</Note>

### 组织角色

组织角色与[企业功能工作区 RBAC](#workspace-roles-rbac) 不同，用于多个[工作区](#workspaces) 的上下文中。您的组织角色决定了您的工作区成员特性和您的[组织级权限](/langsmith/organization-workspace-operations)。

所选的组织角色也会影响工作区成员资格，如下所述：

- [组织管理员](/langsmith/rbac#organization-admin) 授予管理所有组织配置、用户、计费和工作区的完全访问权限。
    - 组织管理员对组织中的所有工作区具有 `Admin` 访问权限。
- [组织用户](/langsmith/rbac#organization-user) 可以读取组织信息，但无法在组织级别执行任何写操作。组织用户可以添加到部分工作区并按常规分配工作区角色（如果 RBAC 启用），这些角色指定工作区级别的权限。
- [组织查看者](/langsmith/rbac#organization-viewer) 等同于组织用户，但**不能**创建个人访问令牌。（对于自托管，可在 Helm chart 版本 0.11.25+ 中使用）。

### 工作区角色（RBAC）

<Note>
RBAC（基于角色的访问控制）是一项仅适用于企业客户的功能。如果您对此功能感兴趣，[请联系我们的销售团队](https://www.langchain.com/contact-sales)。其他计划默认所有用户使用管理员角色。

角色用于定义用户在工作区内的权限集。有三个内置系统角色无法编辑：

[组织管理员](/langsmith/rbac#organization-admin) 还可以创建/编辑具有不同资源特定权限的自定义角色。

您可以在**组织设置** > **成员和角色**下管理角色，选择**角色**选项卡。

## 最佳实践

### 环境分离

使用[资源标签](#resource-tags) 使用默认标签键 `Environment` 和不同环境值（例如 `dev`、`staging`、`prod`）按环境组织资源。我们不建议使用单独的工作区进行环境分离，因为资源无法跨工作区共享，这会阻止您在环境之间提升资源（如提示词）。

<Note>
**资源标签与提示词管理的提交标签**

虽然两种类型的标签都可以使用环境术语，如 `dev`、`staging` 和 `prod`，但它们用途不同：

- **资源标签**（`Environment: prod`）：使用这些来*组织和过滤*工作区中的资源。将资源标签应用于追踪项目、数据集和其他资源（包括提示词）以按环境分组，从而在 UI 中启用过滤。
- [提交标签](/langsmith/manage-prompts#commit-tags)（`prod` 标签）：使用这些来管理您的代码引用的[提示词版本](/langsmith/prompt-engineering)。提交标签是指向提示词历史记录中特定提交的标签。当您的代码按标签名称拉取提示词时（例如 `client.pull_prompt("prompt-name:prod")`），它会检索该标签当前指向的任何提交。要将提示词从 `staging` 提升到 `prod`，请移动提交标签以指向所需版本。

资源标签组织**哪些资源**属于环境。提交标签让您可以控制您的代码引用提示词的**哪个版本**，而无需更改代码本身。
</Note>

## 使用和计费

### 数据保留

本节介绍数据保留如何工作以及在 LangSmith 中如何定价。

#### 为什么保留很重要

* **隐私**：许多数据隐私法规，如欧洲的 GDPR 或加州的 CCPA，要求组织在个人数据不再用于收集目的后将其删除。设置保留期有助于符合此类法规。
* **成本**：LangSmith 对具有低数据保留的追踪收费较低。有关更多信息，了解如何[强制执行消费限制](/langsmith/billing#enforce-spend-limits)。

#### 它是如何工作的

LangSmith 根据数据保留有两个层级的追踪，具有以下特征：

| | 基础 | 扩展 |
| -------------------- | ---------------- | -------------- |
| **价格** | [见定价页面](https://www.langchain.com/pricing-langsmith) | [见定价页面](https://www.langchain.com/pricing-langsmith) |
| **保留期** | 14 天 | 400 天 |

**保留结束后的数据删除**

在指定保留期后，追踪将不再可通过追踪项目 UI 或 API 访问。此后一天内，与追踪关联的所有用户数据（例如输入和输出）将从我们的内部系统中删除。为分析和计费目的，可能会无限期保留与每个追踪关联的某些元数据。

#### 数据保留自动升级

<Warning>
自动升级可能会影响您的账单。请仔细阅读本节以完全了解您预计的 LangSmith 追踪成本。
</Warning>

当您对 `基础` 层追踪使用某些功能时，其数据保留将自动升级到 `扩展` 层。这将增加追踪的保留期和成本。

追踪升级时的完整场景列表：

* **反馈**被添加到追踪的任何运行上（或线程中的任何追踪上），无论是通过[手动标注](/langsmith/annotate-traces-inline)、使用[在线评估器](/langsmith/online-evaluations-llm-as-judge)自动进行，还是通过 [SDK](/langsmith/attach-user-feedback) 以编程方式进行。
* [标注队列](/langsmith/annotation-queues#assign-runs-to-a-single-run-queue) 从追踪中接收任何运行。
* [自动化规则](/langsmith/rules#create-a-rule) 匹配追踪中的任何运行。

**为什么自动升级追踪？**

我们在追踪自动升级模型背后有两个原因：

1. 我们认为符合任何这些条件的追踪从根本上比其他追踪更有趣，因此让用户能够将它们保留更长时间是好的。
2. 从哲学上讲，我们希望对可能没有有意义交互的追踪收取低一个数量级的费用。我们认为自动升级使我们的定价模型与 LangSmith 带来的价值保持一致，只有具有有意义交互的追踪才会以更高的费率收费。

如果您对我们的定价模型有疑问或顾虑，请随时通过 [support.langchain.com](https://support.langchain.com) 联系支持人员并告诉我们您的想法！

**数据保留如何影响下游功能？**

* **标注队列、运行规则和反馈**：使用这些功能的追踪将被[自动升级](#data-retention-auto-upgrades)。
* **监控**：监控标签页即使在基础层追踪的数据保留期结束后仍将继续工作。它由存在超过 30 天的追踪元数据驱动，这意味着您的监控图表即使在 `基础` 层追踪上也将保持准确。
* **数据集**：数据集具有无限的数据保留期。换句话说，如果您将追踪的输入和输出添加到数据集，它们永远不会被删除。我们建议，如果您使用 LangSmith 进行数据收集，请利用数据集功能。

#### 计费模型

**计费指标**

在您的 LangSmith 发票上，您会看到我们收费的两个指标：

* LangSmith 追踪（基础费用）
* LangSmith 追踪（扩展数据保留升级）。

第一个指标包括所有追踪，不分层级。第二个指标仅计算扩展保留追踪的数量。

**为什么测量所有追踪 + 升级而不是基础和扩展追踪？**

在考虑我们的定价时，一个很自然的问题是为什么不直接在发票上显示 `基础` 层和 `扩展` 层追踪的数量？

虽然我们理解这会更简单，但它不能正确地适应追踪升级。考虑一个在 6 月 30 日记录的 `基础` 层追踪，在 7 月 3 日升级到 `扩展` 层。`基础` 层追踪发生在 6 月计费期间，但升级发生在 7 月计费期间。因此，我们需要能够独立衡量这两个事件，以便正确地向客户收费。

如果您的追踪被记录为扩展保留追踪，则 `基础` 和 `扩展` 指标都将以相同的时间戳记录。

**成本细分**

追踪的基础费用为每次追踪 0.05¢。我们将升级定价为扩展保留追踪的成本是基础层追踪的 10 倍（每次追踪 0.50¢），包括两个指标。因此，每次升级的费用为 0.45¢。

### 速率限制

LangSmith 有速率限制，旨在确保所有用户服务的稳定性。

为确保访问和稳定性，在以下情况下，LangSmith 将响应 HTTP 状态代码 429，表明超过了速率或使用限制：

#### 应用负载均衡器上一分钟期间的临时吞吐量限制

此 429 是由于在每服务密钥或 PAT 基础上的一分钟窗口内超过了固定数量的 API 调用而导致的。窗口的开始会有所不同——不保证在时钟分钟的开始，并且可能根据应用程序部署事件而变化。

在收到最大事件后，我们将响应 429，直到从评估窗口开始达到 60 秒，然后重复此过程。

此 429 由我们的应用程序负载均衡器抛出，是为所有 LangSmith 用户设置的服务连续性机制，独立于计划层级。

| 方法 | 端点 | 限制 | 窗口 |
| ----------------- | ------------- | ----- | -------- |
| `DELETE` | `/sessions*` | 30 | 1 分钟 |
| `POST` OR `PATCH` | `/runs*` | 5000 | 1 分钟 |
| `GET` | `/runs/:id` | 30 | 1 分钟 |
| `POST` | `/feedbacks*` | 5000 | 1 分钟 |
| `*` | `*` | 2000 | 1 分钟 |

<Note>
LangSmith SDK 采取措施通过将来自单个会话 ID 的最多 100 个运行批量处理到单个 API 调用中来最大程度地减少达到这些限制的可能性。
</Note>

#### 计划级每小时追踪事件限制

此 429 是由于达到最大每小时事件摄入量而导致的，在 UTC 每个时钟小时开始时评估的固定窗口中，并在每个新小时顶部重置。

此上下文中的事件是运行的创建或更新。如果在相同时段窗口中创建了一个运行然后随后更新，则该运行算作此限制的 2 个事件。

这是由我们的应用程序抛出的，因计划层级而异，Startup/Plus 和企业计划层级的组织比设计和供个人使用的免费和开发者计划层级具有更高的每小时限制。

| 企业 | 自定义 | 自定义 |

#### 计划级每小时追踪数据摄入限制

此 429 是由于超过追踪输入、输出和元数据摄入的最大数据量而导致的，在 UTC 每个时钟小时开始时评估的固定窗口中，并在每个新小时顶部重置。

这是由我们的应用程序抛出的，因计划层级而异，Startup/Plus 和企业计划层级的组织比设计和供个人使用的免费和开发者计划层级具有更高的每小时限制。

| 开发者（已有付款记录） | 2.5GB | 1 小时 |
| Startup/Plus | 5.0GB | 1 小时 |
| 企业 | 自定义 | 自定义 |

### 使用限制

LangSmith 允许您配置追踪的使用限制。请注意，这些是*使用*限制，不是*消费*限制，这意味着它们允许您限制某些事件的occurrence数量，而不是您将花费的总额。

LangSmith 允许您设置两个不同的每月限制，与前面数据保留指南中讨论的计费指标相对应：

* 所有追踪限制
* 扩展数据保留追踪限制

这些允许您分别限制总追踪数量和扩展数据保留追踪数量。

#### 使用限制的特性

使用限制是近似值，这意味着我们不保证限制的准确性。在极少数情况下，在使用限制开始适用之前，可能会有一小段时间处理超过限制阈值的额外追踪。

#### 扩展数据保留追踪限制的副作用

扩展数据保留追踪限制有副作用。如果限制已达到，则任何可能导致追踪层级自动升级的功能都会变得不可访问。这是因为追踪的自动升级会导致创建另一个扩展保留追踪，而这反过来不应该被限制允许。因此，您将不再能够：

1. 匹配运行规则
2. 向追踪添加反馈
3. 向标注队列添加运行

这些功能中的每一个都可能导致自动升级，因此当达到限制时我们会关闭它们。

#### 更新使用限制

使用限制可以从**设置**页面的**使用和计费**下更新。限制值会被缓存，因此可能需要一两分钟才能应用新限制。
