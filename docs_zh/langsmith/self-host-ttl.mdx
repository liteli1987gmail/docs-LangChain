LangSmith Self-Hosted 允许启用追踪的自动 TTL 和数据保留。如果你正在遵守数据隐私法规，或者你想要更有效地使用空间并自动清理追踪，这会很有用。追踪的数据保留期也会根据某些操作或运行规则应用自动延长。

<Note>
**自托管 [Enterprise](/langsmith/pricing-plans) 客户：**你现在可以通过 UI 在工作区级别配置扩展数据保留，这提供了更细粒度的控制，无需更改环境变量。有关详细信息，请参阅[自定义扩展保留策略](/langsmith/data-purging-compliance#customize-extended-retention-policy)。本文档中记录的系统范围 TTL 配置仍然受支持。
</Note>

## 要求

你可以通过 helm 或环境变量设置来配置保留。有几个可配置的选项：

- *Enabled：*数据保留是启用还是禁用。如果启用，通过 UI 你可以将默认组织和项目 TTL 层级应用于追踪（请参阅[数据保留指南](/langsmith/administration-overview#data-retention)了解更多详情）。
- *保留期：*你可以为短期和长期追踪配置系统范围的保留期。配置后，你可以管理每个项目的保留级别，也可为新项目设置组织范围的默认值。

<CodeGroup>

```yaml Helm
config:
  ttl:
    enabled: true
    ttl_period_seconds:
      # -- 400 天长期和 14 天短期
      longlived: "34560000"
      shortlived: "1209600"
```

```bash Docker
# 在你的 .env 文件中FF_TRACE_TIERS_ENABLED=trueTRACE_TIER_TTL_DURATION_SEC_MAP='{"longlived": 34560000, "shortlived": 1209600}'
```

</CodeGroup>

## ClickHouse TTL 清理作业

从版本 **0.11** 开始，一个 cron 作业在周末运行，以帮助删除 ClickHouse 内置 TTL 机制可能未能清理的过期数据。

<Warning>
此作业使用潜在长时间运行的 **mutations**（`ALTER TABLE DELETE`），这是会影响 ClickHouse 性能的昂贵操作。我们建议仅在非高峰时间（夜间和周末）运行这些操作。在使用 **1 个并发活动** mutation（默认值）进行测试时，我们没有观察到 CPU、内存或延迟的显著增加。
</Warning>

### 默认计划

默认情况下，清理作业运行：

- **周六**：UTC 晚上 8 点和 10 点
- **周日**：UTC 上午 12 点、2 点和 4 点

### 禁用作业

要完全禁用清理作业：

```yaml
queue:
  deployment:
    extraEnv:
      - name: "ENABLE_CLICKHOUSE_TTL_CLEANUP_CRON"
        value: "false"
```
### 配置计划

你可以通过修改 cron 表达式来自定义清理作业的运行时间：
```yaml
queue:
  deployment:
    extraEnv:
      # UTC：周日 12am/2am/4am
      - name: "CLICKHOUSE_TTL_CLEANUP_CRON_WEEKEND_MORNING"
        value: "0 0,2,4 * * 0"
      # UTC：周六 8pm/10pm
      - name: "CLICKHOUSE_TTL_CLEANUP_CRON_WEEKEND_EVENING"
        value: "0 20,22 * * 6"
```
<Tip>
要使用单个 cron 计划运行作业，请将 `CLICKHOUSE_TTL_CLEANUP_CRON_WEEKEND_EVENING` 和 `CLICKHOUSE_TTL_CLEANUP_CRON_WEEKEND_MORNING` 设置为相同的值。作业锁定可防止重叠执行。
</Tip>

### 配置每部分最少过期行数

作业逐表进行，扫描部分并从包含最少过期行的部分中删除数据。此阈值平衡了效率和彻底性：

- **过低**：作业扫描整个部分以清除最少数据（效率低）
- **过高**：作业遗漏具有大量过期数据的部分

```yaml
queue:
  deployment:
    extraEnv:
      - name: "CLICKHOUSE_TTL_CRON_MIN_EXPIRED_ROWS_PER_PART"
        value: "100000" # 10 万过期行
```

#### 检查过期行

使用此查询分析表中的过期行，并相应地调整你的最小值：

```sql
-- Runs 表的查询。对于其他表，将 'ttl_seconds' 替换为 'trace_ttl_seconds'
SELECT
    _part,
    count() AS expired_rows
FROM runs
WHERE trace_first_received_at IS NOT NULL
AND ttl_seconds IS NOT NULL
AND toDateTime(assumeNotNull(trace_first_received_at) + toIntervalSecond(assumeNotNull(ttl_seconds))) < now()
GROUP BY _part
ORDER BY expired_rows DESC
```

### 配置最大活动 mutations

删除操作可能耗时较长（约 100GB 部分约 50 分钟）。你可以增加并发 mutations 以加快该过程：

```yaml
queue:
  deployment:
    extraEnv:
      - name: "CLICKHOUSE_TTL_CRON_MAX_ACTIVE_MUTATIONS"
        value: "1"
```

<Warning>
增加并发删除操作可能会严重影响系统性能。仔细监控你的系统，并且仅在你能够容忍可能更慢的插入和读取延迟时才增加此值。
</Warning>

### 紧急情况：停止正在运行的 mutations

如果你遇到延迟峰值并需要终止正在运行的 mutation：

1. **查找活动 mutations**：

   ```sql
   SELECT * FROM system.mutations WHERE is_done = 0;
   ```

   查找 `command` 列包含 `DELETE` 语句的 `mutation_id`。

2. **终止 mutation**：
   ```sql
   KILL MUTATION WHERE mutation_id = '<mutation_id>';
   ```

### 备份和数据保留

如果运行此作业后磁盘空间没有减少，或者继续增加，备份可能通过创建文件系统硬链接导致问题。这些链接阻止 ClickHouse 清理数据。

要验证，请检查 ClickHouse pod 内的以下目录：

 - `/var/lib/clickhouse/backup`
 - `/var/lib/clickhouse/shadow`

如果存在备份，将它们复制到外部文件系统或 blob 存储（例如 S3），然后清除目录。几分钟后，你会注意到磁盘空间释放。
