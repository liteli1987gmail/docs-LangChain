LangSmith Agent Server 的默认配置旨在处理各种不同工作负载的大量读写负载。通过遵循以下概述的最佳实践，您可以调整 Agent Server 以在特定工作负载下获得最佳性能。本页面描述了 Agent Server 的扩展注意事项，并提供了帮助配置部署的示例。

<Tip>
如果您还不熟悉 API 服务器和队列工作线程在容器级别如何操作，请先阅读[运行时架构](/langsmith/agent-server#runtime-architecture)概述。
</Tip>

有关一些自托管配置示例，请参阅[扩展示例 Agent Server 配置](#example-self-hosted-agent-server-configurations)部分。

## 扩展写负载

写负载主要由以下因素驱动：

- 创建新的[运行](/langsmith/background-run)
- 在运行执行期间创建新的检查点
- 写入长期记忆
- 创建新的[线程](/langsmith/use-threads)
- 创建新的[助手](/langsmith/assistants)
- 删除运行、检查点、线程、助手和 cron 作业

以下组件主要负责处理写负载：

- API 服务器：处理初始请求和将数据持久化到数据库。
- 队列工作线程：处理运行的执行。
- Redis：处理关于正在运行的临时数据的存储。
- Postgres：处理所有数据的存储，包括运行、线程、助手、cron 作业、检查点和长期记忆。

### 扩展写路径的最佳实践

#### 根据助手特性更改 `N_JOBS_PER_WORKER`

[`N_JOBS_PER_WORKER`](/langsmith/env-var#n_jobs_per_worker) 的默认值是 10。您可以更改此值以扩展单个队列工作线程可以同时执行的最大运行数，基于您助手的特性。

更改 `N_JOBS_PER_WORKER` 的一些通用指南：

- 如果您的助手受 CPU 限制，默认值 10 可能就足够了。如果您发现队列工作线程上的 CPU 使用率过高或运行执行延迟，您可能会降低 `N_JOBS_PER_WORKER`。
- 如果您的助手受 IO 限制，请增加 `N_JOBS_PER_WORKER` 以处理每个工作线程更多并发运行。

`N_JOBS_PER_WORKER` 没有上限。但是，队列工作线程在获取新运行方面是贪婪的，这意味着它们会尝试拾取尽可能多的可用运行并立即开始执行它们。在具有突发流量的环境中，将 `N_JOBS_PER_WORKER` 设置得太高可能导致工作线程利用不均衡和运行执行时间增加。

#### 避免同步阻塞操作

在代码中避免同步阻塞操作，并优先使用异步操作。长时间的同步操作可能会阻塞主事件循环，导致更长的请求和运行执行时间以及潜在的超时。

例如，考虑一个需要睡眠 1 秒的应用程序。不要使用如下同步代码：
```python
import time

def my_function():
    time.sleep(1)
```

而要使用异步代码：
```python
import asyncio

async def my_function():
    await asyncio.sleep(1)
```

如果助手需要同步阻塞操作，请在 `asyncio.to_thread()` 或等效操作中运行这些操作。

#### 最小化冗余检查点

通过将 [`durability`](/oss/python/langgraph/durable-execution#durability-modes) 设置为确保数据持久化所需的最小值来最小化冗余检查点。

默认持久化模式是 `"async"`，意味着检查点异步地在每一步之后写入。如果助手只需要持久化运行的最终状态，则可以将 `durability` 设置为 `"exit"`，仅存储运行的最终状态。这可以在创建运行时设置：

```python
from langgraph_sdk import get_client

client = get_client(url=<DEPLOYMENT_URL>)
thread = await client.threads.create()
run = await client.runs.create(
    thread_id=thread["thread_id"],
    assistant_id="agent",
    durability="exit"
)
```

#### 自托管

<Note>
这些设置仅对[自托管](/langsmith/self-hosted)部署是必需的。默认情况下，[云](/langsmith/cloud)部署已启用这些最佳实践。
</Note>

##### 启用队列工作线程的使用 <a name="enable-the-use-of-queue-workers"></a>

默认情况下，API 服务器管理队列，不使用队列工作线程。您可以通过将 `queue.enabled` 配置设置为 `true` 来启用队列工作线程的使用。

```yaml
queue:
  enabled: true
```

这将允许 API 服务器将队列管理卸载到队列工作线程，显著减少 API 服务器上的负载，并允许它专注于处理请求。

##### 支持等于预期吞吐量的作业数

您并行执行的运行越多，您需要处理的负载就越多。有两个主要参数可以扩展可用作业：

- `number_of_queue_workers`：配置的队列工作线程数。
- `N_JOBS_PER_WORKER`：单个队列工作线程可以同时执行的运行数。默认为 10。

您可以使用以下公式计算可用作业：
```
available_jobs = number_of_queue_workers * `N_JOBS_PER_WORKER`
```

吞吐量是可用作业每秒可以执行的运行数：
```
throughput_per_second = available_jobs / average_run_execution_time_seconds
```

因此，您应该配置以支持预期稳态吞吐量的最小队列工作线程数为：
```
number_of_queue_workers = throughput_per_second * average_run_execution_time_seconds / `N_JOBS_PER_WORKER`
```

##### 为突发工作负载配置自动扩展 <a name="configure-autoscaling-for-bursty-workloads-write"></a>

默认情况下自动扩展是禁用的，但应该为突发工作负载进行配置。使用与[上一节](#support-a-number-of-jobs-equal-to-expected-throughput)相同的计算，您可以确定自动扩展器应该扩展到的最大队列工作线程数，基于最大预期吞吐量。

## 扩展读负载

读负载主要由以下因素驱动：

- 获取[运行](/langsmith/background-run)的结果
- 获取[线程](/langsmith/use-threads)的状态
- 搜索[运行](/langsmith/background-run)、[线程](/langsmith/use-threads)、[cron 作业](/langsmith/cron-jobs)和[助手](/langsmith/assistants)
- 检索检查点和长期记忆

以下组件主要负责处理读负载：

- API 服务器：处理请求并直接从数据库检索数据。
- Postgres：处理所有数据的存储，包括运行、线程、助手、cron 作业、检查点和长期记忆。
- Redis：处理关于正在运行的临时数据的存储，包括从队列工作线程到 API 服务器的流式消息。

### 扩展读路径的最佳实践

#### 使用过滤来减少每个请求返回的资源数量

[Agent Server](/langsmith/agent-server) 为每种资源类型提供了搜索 API。这些 API 默认实现分页，并提供许多过滤选项。使用过滤来减少每个请求返回的资源数量并提高性能。

#### 设置 TTL 以自动删除旧数据

设置[线程上的 TTL](/langsmith/configure-ttl) 以自动清理旧数据。当关联的线程被删除时，运行和检查点会自动删除。

#### 避免轮询，使用 /join 来监控运行状态

避免通过使用 `/join` API 端点轮询运行状态。此方法在运行完成后返回运行的最终状态。

如果您需要实时监控运行输出，请使用 `/stream` API 端点。此方法流式传输运行输出，包括运行的最终状态。

#### 自托管

<Note>
这些设置仅对[自托管](/langsmith/self-hosted)部署是必需的。默认情况下，[云](/langsmith/cloud)部署已启用这些最佳实践。
</Note>

##### 为突发工作负载配置自动扩展 <a name="configure-autoscaling-for-bursty-workloads-read"></a>

默认情况下自动扩展是禁用的，但应该为突发工作负载进行配置。您可以确定自动扩展器应该扩展到的最大 API 服务器数，基于最大预期吞吐量。[云](/langsmith/cloud)部署的默认最大 API 服务器数为 10。

## 扩展示例自托管 Agent Server 配置

<Note>
确切的最佳配置取决于您的应用程序复杂性、请求模式和数据需求。将以下示例与前几节中的信息和您的特定用法结合使用，根据需要更新部署配置。如果您有任何问题，请通过 [support.langchain.com](https://support.langchain.com) 联系支持人员。
</Note>

下表提供了不同 LangSmith Agent Server 配置的概述比较，用于各种负载模式（每秒读请求/每秒写请求）和标准助手特性（平均运行执行时间为 1 秒，中等 CPU 和内存使用）：

|  | **[低 / 低](#low-reads-low-writes)** | **[低 / 高](#low-reads-high-writes)** | **[高 / 低](#high-reads-low-writes)** | [中 / 中](#medium-reads-medium-writes) | [高 / 高](#high-reads-high-writes) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| <Tooltip tip="部署每秒处理的写请求数">每秒写请求</Tooltip> | 5 | 5 | 500 | 50 | 500 |
| <Tooltip tip="部署每秒处理的读请求数">每秒读请求</Tooltip> | 5 | 500 | 5 | 50 | 500 |
| **API 服务器**<br />(1 CPU，每个服务器 2Gi) | 1（默认） | 6 | 10 | 3 | 15 |
| **队列工作线程**<br />(1 CPU，每个工作线程 2Gi) | 1（默认） | 10 | 1（默认） | 5 | 10 |
| **`N_JOBS_PER_WORKER`** | 10（默认） | 50 | 10 | 10 | 50 |
| **Redis 资源** | 2 Gi（默认） | 2 Gi（默认） | 2 Gi（默认） | 2 Gi（默认） | 2 Gi（默认） |
| **Postgres 资源** | 2 CPU<br />8 Gi（默认） | 4 CPU<br />16 Gi 内存 | 4 CPU<br />16 Gi | 4 CPU<br />16 Gi 内存 | 8 CPU<br />32 Gi 内存 |

以下示例配置启用这些设置中的每一个。负载级别定义为：

- 低意味着大约每秒 5 个请求
- 中意味着大约每秒 50 个请求
- 高意味着大约每秒 500 个请求

### 低读，低写 <a name="low-reads-low-writes"></a>

默认的 [LangSmith 部署](/langsmith/deployment) 配置将处理此负载。无需自定义资源配置。

### 低读，高写 <a name="low-reads-high-writes"></a>

您的部署每秒处理大量写请求（500/秒），但读请求相对较少（5/秒）。

为此，我们建议如下配置：

```yaml
# 低读高写配置示例（每秒 5 读/500 写请求）
api:
  replicas: 6
  resources:
    requests:
      cpu: "1"
      memory: "2Gi"
    limits:
      cpu: "2"
      memory: "4Gi"

queue:
  replicas: 10
  resources:
    requests:
      cpu: "1"
      memory: "2Gi"
    limits:
      cpu: "2"
      memory: "4Gi"

config:
  numberOfJobsPerWorker: 50

redis:
  resources:
    requests:
      memory: "2Gi"
    limits:
      memory: "2Gi"

postgres:
  resources:
    requests:
      cpu: "4"
      memory: "16Gi"
    limits:
      cpu: "8"
      memory: "32Gi"
```

### 高读，低写 <a name="high-reads-low-writes"></a>

您有大量读请求（500/秒）但写请求相对较少（5/秒）。

为此，我们建议如下配置：

```yaml
# 高读低写配置示例（每秒 500 读/5 写请求）
api:
  replicas: 10
  resources:
    requests:
      cpu: "1"
      memory: "2Gi"
    limits:
      cpu: "2"
      memory: "4Gi"

queue:
  replicas: 1  # 默认，最小写负载
  resources:
    requests:
      cpu: "1"
      memory: "2Gi"
    limits:
      cpu: "2"
      memory: "4Gi"

redis:
  resources:
    requests:
      memory: "2Gi"
    limits:
      memory: "2Gi"

postgres:
  resources:
    requests:
      cpu: "4"
      memory: "16Gi"
    limits:
      cpu: "8"
      memory: "32Gi"
  # 在高读场景中考虑读取副本
  readReplicas: 2
```

### 中读，中写 <a name="medium-reads-medium-writes"></a>

这是一个平衡的配置，应该处理中等读写负载（每秒 50 读/50 写请求）。

为此，我们建议如下配置：

```yaml
# 中读中写配置示例（每秒 50 读/50 写请求）
api:
  replicas: 3
  resources:
    requests:
      cpu: "1"
      memory: "2Gi"
    limits:
      cpu: "2"
      memory: "4Gi"

queue:
  replicas: 5
  resources:
    requests:
      cpu: "1"
      memory: "2Gi"
    limits:
      cpu: "2"
      memory: "4Gi"

redis:
  resources:
    requests:
      memory: "2Gi"
    limits:
      memory: "2Gi"

postgres:
  resources:
    requests:
      cpu: "4"
      memory: "16Gi"
    limits:
      cpu: "8"
      memory: "32Gi"
```

### 高读，高写 <a name="high-reads-high-writes"></a>

您有大量读写请求（每秒 500 读/500 写请求）。

为此，我们建议如下配置：

```yaml
# 高读高写配置示例（每秒 500 读/500 写请求）

  replicas: 15

      memory: "2Gi"
    limits:
      memory: "2Gi"

  resources:
    requests:
      cpu: "8"
      memory: "32Gi"
    limits:
      cpu: "16"
      memory: "64Gi"
```

### 自动扩展

如果您的部署遇到突发流量，您可以启用自动扩展以扩展 API 服务器和队列工作线程的数量来处理负载。

以下是针对高读和高写的自动扩展示例配置：

```yaml
api:
  autoscaling:
    enabled: true
    minReplicas: 15
    maxReplicas: 25

queue:
  autoscaling:
    enabled: true
    minReplicas: 10
    maxReplicas: 20
```

<Note>
确保您的部署环境有足够的资源扩展到建议的大小。监控您的应用程序和基础设施以确保最佳性能。考虑实施监控和警报以跟踪资源使用和应用程序性能。
</Note>
